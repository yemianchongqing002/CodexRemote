# 排队、引导与项目内新建会话

## 网页操作

- 项目节点右侧 `＋` 打开新建窗口，填写第一条消息，点击“创建并发送”。在项目的现有目录运行，使用电脑 Codex 的默认配置，不建立额外 worktree。
- 输入框旁只保留“发送”，点击后默认排队并清空输入框。排队卡片展示消息正文，右侧的“删除”取消排队，“引导”立即投递这条排队消息。
- 每个聊天最多保存 5 条排队消息（含正在投递的消息），按入队顺序等待；满额后保留草稿，等待投递或删除后可继续添加。第一条正文最多显示两行，其余各显示一行，每条保留删除和引导按钮；队列区域限制高度并内部滚动。引导复用该条排队请求的 ID，原子移出自动调度，重复点击不会重复发送，也不会清空输入框中新写的草稿。
- 排队卡片显示等待和投递状态，确认送达后自动消失；失败或结果未确认时保留提示。开始投递前可以删除；开始投递后不能撤回。进入后台或关闭网页不会取消电脑队列。
- 聊天被中断、未发现完成记录或状态未知时，队列继续等待，可取消或改用立即引导。审批可在电脑桌面或[客户端审批卡片](remote-controls.md)处理。

## 排队实现与边界

### 模型、Fast 与思考深度

输入框右下角选择模型、思考深度和 Fast，修改自动保存在当前连接、当前聊天的本地草稿中，随下一条消息发送，无需应用按钮。未修改时不携带设置，沿用桌面配置。模型列表按需读取并缓存五分钟，不支持 Fast 的模型禁用开关。

设置随消息保存到电脑队列，投递时才传给桌面；之后修改不影响已排队消息。入队确认后清除本地待发送设置，失败或结果未确认时保留。选择空选项可取消本地修改；恢复按钮还原所选模型默认深度并关闭 Fast。

携带模型设置的消息必须等待下一轮，不能立即引导当前轮。普通排队消息仍可引导。新建聊天使用电脑默认配置，权限与审批沿用桌面设置。

发送按钮使用上箭头。正在回答且输入框为空时切换为停止；有草稿时保留发送和独立停止按钮。停止携带当前轮标识，避免延迟请求误停下一轮；不会删除草稿或队列。中断后队列等待正常完成记录。当前轮标识不可读时不提供停止，刷新后再确认。

读取模型需要可运行的本机 Codex；发送和停止需要桌面运行及正确 IPC 配置。

### 图片输入

输入区“＋ 图片”可从手机相册或电脑选择 PNG、JPEG、GIF；电脑也可以在输入框粘贴剪贴板图片，或将图片拖入输入区。每条消息最多 4 张，每张最多 8 MiB、4000 万像素。HEIC/WebP 需先转成支持的格式。可只发送图片，也可附带文字；上传期间不能提交，失败时可移除重选。缩略图旁的移除按钮仅移出当前草稿。

图片先通过已登录的同源接口上传到运行服务的电脑，再以受校验的图片 ID 随消息排队。后端仅将自己保存的图片转换为桌面 `localImage` 输入，不接受浏览器提供任意本机路径。图片也参与请求防重校验；队列和图片引用可随服务重启恢复。浏览器中已上传的图片草稿引用保存在当前标签页的 sessionStorage，App 使用按连接隔离的本地存储，刷新后可恢复；尚未上传完成的图片需重新选择，退出登录会清空草稿引用。

图片保存在口令文件同级的 `outbox.jsonl.queue.images/`，目录容量上限 256 MiB。图片按内容去重，元数据只记录图片 ID；为保留桌面历史中的本地图片引用，发送、取消或移除草稿后不会自动删除图片文件。达到容量后需在电脑维护该目录，删除前确认不再用于待发送队列或需要保留的历史。分发包不包含图片或口令。

发送后的历史由目标电脑日志回读，图片按日志中的本地路径从目标电脑加载，不经过模型重新生成。App 对成功加载的媒体使用有容量限制的内存缓存，退出后释放；目标电脑的图片文件仍是持久来源。Windows 路径按原始引用保留，避免 Markdown 把反斜杠解析成转义符。

粘贴依赖浏览器向粘贴事件提供图片文件；部分手机浏览器或剪贴板来源仅提供文字，此时使用“＋ 图片”选图。此实现不需要主动读取系统剪贴板，因此不依赖 Clipboard API 的 HTTPS 权限。新建会话弹窗仍仅支持首条文字，图片用于已有聊天。

电脑 outbox 先保存 `queued` 元数据，正文保存到 `outbox.jsonl.queue/<requestId>`（目录 0700、文件 0600）。正文大小最多 16 KiB，全局最多 32 条等待消息。元数据含正文摘要和模式，不含正文。重启会校验并恢复尚未投递的正文；投递结束或取消后删除独立正文文件。发送中断后结果不明的 `pending` 恢复为 `unknown`，不会自动重发。

仅在存在排队消息时，电脑每 500 毫秒增量检查对应聊天的落盘状态，空队列休眠，新消息入队唤醒。要求两次连续读取相同的完成版本、文件已经完整读到末尾、没有残缺行、不是归档或中断状态。发现桌面接收方后，再检查一次状态；如果又开始工作，返回队列。排队投递只使用 follower start，不自动退回 steer。查看器继续使用原有 SSE；outbox 变化立即触发通知，不再等待常规 3 秒检查，手机后台不保持连接。

这是根据本机日志判断完成的适配，并不是桌面队列的原子操作：当前 follower start 没有“仅当空闲才接受”的条件参数。如果其他桌面窗口恰在最后一次检查与投递之间开启新一轮，仍有竞态窗口。桌面内部的 `set-queued-follow-ups-state` 会整批替换队列，因此这里不修改它，避免覆盖用户桌面的原有排队消息。

多条排队按原始入队时间依次处理，每轮只检查每个聊天最早的一条。自动投递会持久化所使用的完成版本；已接受或结果不明的投递不会再次使用同一完成版本触发下一条，服务重启后也保留此约束。下一条等待新的完成记录，并再次通过稳定状态检查；投递前发现忙碌而退回队列时保留原始顺序。“引导”仍可手动选择某一条立即投递。

## 新建实现

`POST /api/thread/create` 仅接受列表中已有且当前存在的项目目录、请求 ID 和首条消息。服务通过独立的本机 `codex app-server --stdio` 执行 initialize、thread/start、thread/inject_items、thread/unsubscribe；不恢复已有聊天，不执行模型生成，不处理审批。

创建会话要求填写首条消息，以便持久化后交给桌面处理。通过官方历史接口保存这条真实输入，unsubscribe 后终止创建器并等待进程退出以释放写入锁，再以 `codex://threads/<id>` 在桌面打开。发现桌面 owner 后，使用空 input 的新一轮启动让桌面继续处理已保存的首条消息，不重复插入消息。创建器按需启动并退出，没有额外常驻 app-server。

首条导入消息带 `codex-remote-initial-` ID 前缀，日志读取器在切换到 canonical 事件时保留它。创建请求与发送共用持久化防重复日志；相同 ID 的项目或首条消息发生变化会被拒绝。不确定结果不会自动重新创建。若会话已保存但桌面启动未确认，返回 `created_unconfirmed`，网页保留创建窗口、原文和核对提示，不按成功关闭，不自动重新创建。只有正常完成接管才返回 `created`（显式关闭桌面接管的隔离模式除外）。

可用 `--codex-binary` 指定本机创建器路径；`--open-created-in-desktop=false` 只创建并保存首条消息，不自动在桌面打开或生成回复，主要用于隔离测试。macOS 默认使用桌面内置程序；Windows/Linux 从 PATH 查找，也可显式指定路径。
