# 发送协议与回执

网页/App 的已有聊天发送经目标电脑上的服务 A，进入该电脑 Codex 桌面的 follower IPC。查看通过日志同步，发送使用桌面聊天原有的模型与权限，审批可在桌面或[远程客户端](remote-controls.md)处理。

## 桌面接口

Windows 使用本机命名管道，macOS/Linux 使用 Unix socket。帧为 4 字节 little-endian 长度前缀加 JSON。初始化版本为 0，owner discovery 为 1，follower steer 为 1、start 为 2。

每次投递建立短连接，发现聊天 owner 后限定后续请求目标。网页不能指定任意方法、管道或主机 ID；模型和访问权限通过专用设置接口校验。follower 是桌面内部协议，兼容性范围见[验证说明](verification.md)。

默认找不到接收方时，服务请求桌面打开对应聊天并重新确认。`--open-thread-on-send=false` 可关闭此行为；`--probe-thread` 始终只读。

## 排队与引导

输入框默认提交到服务端队列；自动投递使用 follower start。队列上的“引导”使用相同请求 ID 立即投递：先 steer，只有明确返回没有活动轮次时才尝试 start。请求结果不确定时不自动重发。

队列状态、图片以及新建流程见[排队与创建](queue-and-create.md)。

## 回执与防重

- 每次提交使用独立 requestId，同时用于桌面 clientUserMessageId。
- outbox 元数据保存请求 ID、目标、内容摘要和回执，写入后再投递。相同 ID 与内容返回原状态；同 ID 不同内容返回冲突。
- `pending` 为处理中，`accepted` 为桌面已确认，`failed` 为未发送或明确拒绝，`unknown` 为结果待核对。“已送达”不代表模型已完成。
- 重启时未确认的投递恢复为 `unknown`，不自动重发。浏览器/App 返回前台后查询已提交请求。
- 等待投递的正文单独保存在队列目录，图片保存在图片目录；outbox 元数据本身不保存正文。

浏览器草稿及待确认请求保存在当前标签页的 sessionStorage；App 使用按连接隔离的本地存储。发送结果不能仅依据输入框是否清空判断。

## 访问控制

发送默认开启，`--read-only` 关闭发送、排队和创建。接口沿用登录口令、Cookie、Host 和 Origin 检查；原始 IPC 不对网络开放。查看和发送权限由服务配置决定。

## 桌面暂未响应时的自动重试

确认消息尚未提交到桌面时（连接失败、接收方探测失败或发送前断开），服务端每隔 30 秒重试，最多尝试 3 次（首次加 2 次重试）。等待期间维持 pending，显示重试进度，保留原请求 ID、正文、附件及模型设置，并占用该聊天的发送位置，避免并发重复投递。关闭网页不会中止重试；正常停止服务会取消尚未执行的重试。

已提交但回执丢失、部分写入、桌面路由超时等结果不确定的情况不自动重发；明确权限拒绝或不兼容结果也不重试。服务重启后仍沿用 pending 转 unknown 的核对规则，不自动恢复不确定的投递。此次重试适用于排队发送和立即引导，不重新创建会话。
